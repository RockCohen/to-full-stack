## 门诊 1 · bug1_loop_var_capture.ts

**症状复盘**:循环结束后 i = 3;三个回调共享同一个 var 变量 i,触发时读到的全是 3,`orders[3]` 是 undefined。

**根因**:`var` 是函数级作用域——整个函数一个盒子,三次迭代共用;闭包捕获的是"盒子的地址",不是当时的值。`let` 每轮迭代一个新绑定,三个回调各抓各的。

**最小修复**:`for (let i = 0; ...)`。

**后端对照**:Java 匿名内部类强制捕获 final——语言替你把"共享盒子"堵死了;JS 的 var 是敞开的门,let 是补上的选择权。

**变体思考**:如果循环体是 `await` 异步调用(每轮等上一轮),var 的行为会变吗?(提示:串行时 i 不再"抢先跑完",但共享仍是隐患。)

## 门诊 2 · bug2_listener_leak.ts

**症状复盘**:每进一次详情页就 `addEventListener` 一次,从不移除;三个监听器各抓着一份 10 万行明细,一次 resize 触发三次刷新——逻辑重复 + 内存持续上涨。

**根因**:订阅没有退订。监听器闭包抓着 bigPayload,GC 永远够得着它——**可达性不理会"你还用不用"**。

**最小修复**:注册时保存句柄,离开页面时移除;或让注册函数返回退订函数:

```ts
function enterDetailPage(orderId: string): () => void {
  const h = () => { ... };
  addEventListener(h);
  return () => removeEventListener(h);   // 离开页面时调用
}
```

**后端对照**:每次建连不 close,连接池被打满——监听器就是前端的"连接"。

**变体思考**:两个监听器都想"只在最后一次注册生效",需要什么语义?(≈ 单播 vs 多播,响应式 store 的 subscribe 是多播。)

## 门诊 3 · bug3_lost_this.ts

**症状复盘**:`onPaid(svc.charge)` 把方法当普通函数传——调用时 `onPaid` 直接执行它,没有点号、没有宿主,严格模式下 this 是 undefined,读 `this.gateway` 抛 TypeError。

**根因**:JS 的 this 由**调用方式**决定;方法脱离对象调用 = 丢上下文。Java 的方法引用天生绑定实例,这个坑 Java 没有独立对应物。

**最小修复**(两种):`onPaid(a => svc.charge(a))`(箭头函数包一层,捕获 svc);或 `onPaid(svc.charge.bind(svc))`(焊死 this)。

**变体思考**:类里写 `charge = (amount: number) => {...}`(箭头函数字段)为什么天生不丢 this?(它在构造时就捕获了实例的 this——写下即绑定。)

## 门诊 4 · bug4_inplace_sort.ts

**症状复盘**:`sort` 是**原地操作**——直接改 orders 的元素顺序。展示列表"排好了",但共享同一份源数据的录入视图也乱了(首笔从 A-001 变成 A-002)。

**根因**:把可变引用交给了"以为只是读"的操作。你改的不是"展示列表",是唯一那份源数据。

**最小修复**:`const sortedView = [...orders].sort(...)`——先拷贝再排序;或用 `toSorted()`(ES2023)。

**后端对照**:把内部可变 List 直接返回给调用方——防御性拷贝(compiler 帮不了你,纪律帮你)。

**变体思考**:数据量百万级,每次展示都拷贝代价高——有什么结构能"多视图共享一份数据、各自有序"?(提示:不可变持久化数据结构,阶段 2 的 Immer/c06 的不可变更新是它的前菜。)

## 门诊 5 · bug5_falsy_discount.ts

**症状复盘**:`if (!discount)` 把 0 判为"没有优惠"——但 0 元优惠码(积分抵扣)是合法输入。`!0 === true`,合法的 0 被"错杀"。

**根因**:JS 会把一切隐式转成布尔:0、''、null、undefined、NaN 全是 **falsy**。后端写惯了 `if (x)`(Java 里编译不过,只收 boolean),肌肉记忆在这里直接变成 bug。

**最小修复**:`if (discount === undefined || discount === null)` 显式判断"没传";或业务上明确"0 无效"就写 `if (!(discount > 0))`——把意图写清楚,别让隐式转换替你做决定。

**后端对照**:Java 编译器在 `if (x)` 处直接编译错误——强类型替你挡了;JS 要靠你自己的显式判断。这是"类型审计左移"失败的经典案例(c00 的回声)。

**变体思考**:`total || defaultTotal` 当 total = 0 时会发生什么?正确的写法是什么?(提示:`??` 空值合并操作符——只对 null/undefined 兜底。)
