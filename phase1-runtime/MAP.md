## 1. 闭包:变量的寿命控制(第①②层)

### 1.1 先看 Java 的墙,再看 JS 的门

Java 有一堵墙:匿名内部类只能捕获 `final` 变量。你背过原因——被捕获的变量要**逃逸到堆上**活过方法生命周期,栈上的可变值做不到,所以语言干脆只放行不可变的。这是语言替你做的安全审查。

JS 没有这堵墙,也没有这份好心。函数可以把任何局部变量**连值带引用**一起带走:

```js
function makeCounter() {
  let count = 0;              // 局部变量,本该随栈帧死亡
  return function () {
    count += 1;               // 但它没死——被内函数抓住了
    return count;
  };
}
const next = makeCounter();
next(); next(); next();       // 1, 2, 3 —— count 活得好好的
```

**这就是闭包的全部**:内函数把定义它的环境(那张"变量表")从栈上**搬到堆上**,变量逃逸了,寿命由"还有没有人抓着它"决定。用你 JVM 的语言说:**主动制造逃逸,换取跨帧存活**——和 React `useState` 的设计动机一模一样(c00/c01 一路铺垫的就是它)。

### 1.2 类比的边界( misunderstanding 高发区 )

- **闭包捕获的是变量,不是值**。三次调用 `makeCounter()` 得到三个独立的 count;但同一次调用返回的多个内函数,共享**同一份** count(一改全改)。对照 Java:匿名内部类捕获的是值的拷贝,JS 传的是"盒子的地址"。
- **`var` 与 `let` 是两个世界**:`var` 的作用域是整个函数(一个函数一个盒子,循环里三次迭代共享同一个 i);`let` 每轮迭代一个新盒子。循环闭包陷阱(门诊 1 号)的根源就在这。
- **闭包是内存泄漏的头号嫌疑人**:抓着大对象不放,GC 就永远不能回收它——可达性分析不看"你还用不用",只看"还够不够得着"。

## 2. this 与原型:调用方注入的上下文(第①②层)

### 2.1 this 不是"我的",是"调用方给的"

Java 的方法天生绑定实例:`order.getTotal()` 里的 `this` 永远是 order,编译期就焊死了。JS 的 `this` 完全不同——**它是一次调用的运行时参数,由调用方式决定**:

```js
order.getTotal();        // this = order(谁点号调,this 是谁)
const fn = order.getTotal; fn();   // this = undefined(严格模式)——"脱离对象调用"
fn.call(order);          // this = order(手动注入)
```

所以"方法作为回调传递后 this 丢失"(门诊 3 号)在 JS 里是**语法层面的必然**,不是 bug 的巧合。对策也熟:箭头函数不绑定自己的 this,**直接捕获外层的**——和 lambda 捕获外部变量同构;或者 `bind(order)` 手动焊死 ≈ `methodReference` 天生绑定的手工版。

### 2.2 原型链:不用 class 的继承,早实现了

对象要读一个自己没有的属性/方法,JS 会沿**原型链**向上找——`order.__proto__` 指向原型对象,原型再指向上游,直到顶点。这是一套**运行时的委托查找**,≈ Java 的方法表/虚分派,但查找发生在每次访问时,且链可以在运行时改。

今天你写的 `class` 只是这套机制的语法糖:编译结果还是原型链。Java 直觉里"class 定义了对象的形状与方法",JS 现实里"对象先存在,方法是查来的"——**先有对象,后有类**,这个次序颠倒值得单独记一笔。

## 3. 内存与 GC:可达性游戏(第③层)

### 3.1 数据放在哪(本题的答卷)

- **调用栈**:原始值(number/string/boolean)与函数帧——随帧生灭,快;
- **堆**:对象、数组、函数(函数在 JS 里是一等公民,是堆上的值)、闭包捕获的环境——由 GC 管;
- **渲染树/Storage**:渲染树在内存但归浏览器管;Storage 是持久层(前端的"磁盘",下一阶段细讲)。

### 3.2 GC = 可达性分析,JVM 同款

V8 的回收判定和你背过的 JVM 一模一样:**从 GC Roots(全局对象、当前调用栈)出发,沿引用走;走不到的,就是垃圾**。所以泄漏只有一种成因:**你以为用完了,引用链还在**——定时器抓着大数组、监听器抓着页面、闭包抓着请求结果。

V8 的算法分代处理(和 JVM 分代收集同构):**新生代**(朝生夕死的临时对象)用 Scavenge 复制算法,快;**老生代**(活得久的)用标记-清除＋整理,慢但省。对一个主线程即生命的浏览器,GC 都要尽量并发/增量做——这是 V8 团队多年的主战场。

**读写世界观落点**:GC 是这台机器上唯一能合法"暂停你的读写"的后台系统——所以它的每一次优化(增量标记、并发回收),都是在保护主线程这个唯一售票窗口(c02 的宪法)。

### 3.3 DevTools 就是你的 jmap/jstat

Chrome DevTools → Memory 面板:堆快照(Heap Snapshot)≈ jmap dump;Allocation instrumentation ≈ 分配剖相;三快照对比法(基准 → 操作 → 再拍,看增量)是你排查线上泄漏的老手艺,快捷键都懒得换。
