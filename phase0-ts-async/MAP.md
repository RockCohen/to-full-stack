## 0. 开场白:三个会让你亏钱的谣言

**谣言一:"JavaScript 是玩具语言。"** 2009 年之前部分属实,现在它是这个星球上部署范围最广的运行时——你写的每一行 Java 服务的调用方,最终都落在某个浏览器进程里。玩具能装下全世界,那说明我们对"玩具"的理解该升级了。

**谣言二:"前端就是画页面的。"** 说这话的人把"渲染"理解成了美工。前端的本质是:在别人的机器上,用一个你无法控制内存、无法起线程、随时可能被杀进程的运行时,完成数据的读写、缓存与展示。约束比后端狠得多,只不过它的"数据库"叫组件状态,它的"锁"叫不可变更新。

**谣言三:"我有 Java 功底,随便看看就会了。"** 最危险的一条。你的功底是真金白银:类型系统、并发、缓存、HTTP,全都直接复用。但前端恰好有几个地方**长得像 Java,行为却相反**——你的直觉会精准地踩进去。本讲义的主要工作,就是把这些雷提前画在地图上。

## 1. TypeScript:看血统,还是看体检报告

### 1.1 结构化类型:TS 不查户口

Java 判断"你是不是 User",看的是**血统**:有没有 `extends User`、类加载器里是不是那个类。TS 判断"你是不是 User",看的是**体检报告**:有 `name` 有 `id`,指标齐了,你就是。

```ts
interface JavaDev  { name: string; spring(): void }
interface ReactDev { name: string; spring(): void }

const me: JavaDev = { name: '老王', spring() {} };
const alias: ReactDev = me;   // ✅ 编译通过——两个类型"长得一样"
```

Java 直觉在这里会大喊"类型不匹配!",TS 说:我又不认识你们俩的爹,我只看指标。这就是**结构化类型(structural typing)** vs **名义类型(nominal typing)**。

### 1.2 但字面量要过更严的安检门

有个反直觉的细节,实验卡里会亲自坑你一次:

```ts
interface Point { x: number }
const a: Point = { x: 1, y: 2 };   // ❌ 编译报错:y 是什么?没申报
const tmp = { x: 1, y: 2 };
const b: Point = tmp;              // ✅ 通过:变量过安检,只查必备项
```

同一个形状,字面量直接赋值被拦,绕道变量就放行。这不是 TS 精神分裂,是**多余属性检查**:对象字面量是"当场新造的人",多出来的字段九成是拼写错误,值得拦一下;而变量可能是"更大类型的子集",拦了反而误伤。

### 1.3 联合类型:Java 里要摆一页纸的东西

Java 表达"成功或失败两种结果",你得写 sealed interface + 两个 record + switch 模式匹配,占半个屏幕。TS 一行:

```ts
type Result =
  | { ok: true;  data: string[] }
  | { ok: false; err: string };
```

更妙的是**收窄(narrowing)**:`if (r.ok)` 之后,TS 静悄悄地把类型缩小到"成功分支",此时 `r.data` 合法、`r.err` 编译报错。这就是你熟悉的"让非法状态不可表示",只不过 Java 靠 sealed + 模式匹配苦哈哈地实现,TS 当成日用品。

配套的还有一个杀手锏 **never**:穷尽 switch 的 default 分支里放一个 `const _exhaustive: never = x`,将来谁加了新分支没处理,编译器立刻在 default 报错——**编译器当证明器用**,等于 sealed interface 的穷尽性检查免费送。

### 1.4 泛型:两兄弟都"擦除",但一个假擦一个真跑路

Java 泛型是**假擦除**:编译后 `List<String>` 变 `List`,元素在运行时是 `Object`,取出来靠编译器偷偷塞的 checkcast 强转——所以你才能 `getDeclaredFields` 反射出泛型签名,也才会有"泛型数组不能 new"的别扭。

TS 泛型是**真蒸发**:编译产物里所有类型痕迹清零,运行时查无此人。这意味着一件 Java 工程师很难第一时间接受的事——**你的 interface 在运行时不存在**。前端拿到的永远是 JSON 字符串,谁告诉你 `port` 字段一定在?没有人。所以 Bean Validation 的活儿在前端没人接,得另请一位:zod 这类运行时校验库(阶段 3 再见它)。记住这个分工:**TS 类型管编译期的法律,zod 管运行时的警察。**

### 1.5 两个小雷

- **readonly ≈ final 引用,不是不可变对象。** `readonly host` 只拦编译期的重新赋值,运行时 `Object.assign` 照改不误——和 Java 的 final 引用一个德行:引用不动,对象照样能被掏。
- **enum 意外是个运行时对象。** 数字枚举编译后是真对象,还带反向映射 `Status[0] === 'Active'`。所以很多 TS 团队禁用 enum,改用字面量联合 `type Status = 'active' | 'frozen'`——既白拿 1.3 节的收窄,又运行时零负担。

## 2. 异步:一个没有 `get()` 的 Future

### 2.1 Promise ≈ CompletableFuture,但有三个本质差异

**差异一:不能阻塞。** `Future.get()` 可以理直气壮地把线程睡到结果回来;Promise 没有对应物,`await` 也不是阻塞——它是**让出**:先把主线程还给队列,自己登记一个"结果到了叫我"的回调。为什么这么设计?因为 JS 主线程是**唯一的售票窗口**,它一睡,页面渲染、点击响应全部停摆。你在 Netty 里早见过这个物种:别让 worker 线程干阻塞的活,注册回调,事件到了再处理。**事件循环就是 Reactor 模式,只是这次雇的 worker 是你的浏览器标签页。**

**差异二:async 函数不创建线程。** Java 里 `CompletableFuture.supplyAsync` 默认扔进 ForkJoinPool——好歹雇了个人。`async function` 一个线程都没雇:它只是把"await 之后的代码"打包成回调挂进队列,然后潇洒离场。所以"前端并发"从来不是"并行计算",是**并发等待**:单线程同时挂起 100 个 I/O,谁的响应先到先处理谁。计算密集?单线程真的会一个一个算。

**差异三:队列分两层,优先级不同。** 微任务(Promise 回调、queueMicrotask)≈ **高优先级就绪队列**,本轮必须清空才肯罢休;宏任务(setTimeout、I/O 回调)≈ **下一个调度周期**。所以 `setTimeout(fn, 0)` 的 0 是"尽快",不是"现在"——它永远排在本轮微任务屁股后面。

### 2.2 前端比后端更记仇:异常不许烂尾

Java 里一个没人 `get()` 的 Future,异常会安静地烂在对象里,谁也不疼谁。前端不行——没人处理的 rejected Promise 触发 `unhandledRejection`,Node 直接给你崩进程,浏览器往控制台甩红字并上报。刚从后端过来的你大概率会写"调了 async 函数却忘了 await,外层 try/catch 形同虚设"这种 bug,坏代码门诊 3 号就是给你准备的。

## 3. 对暗号:映射总表

| Java 后端 | 前端 | 一句话 |
|---|---|---|
| `interface User`(看血统) | `interface User`(看体检) | 结构化 vs 名义类型 |
| sealed interface + 模式匹配 | 联合类型 + 收窄 | 让非法状态不可表示 |
| 泛型假擦除 + 反射 | 泛型真蒸发 + zod | 编译期幻觉,运行时要补票 |
| `Future.get()` | `await` | 一个阻塞,一个让出 |
| 线程池 + worker | 事件循环 + 队列 | 一个雇人,一个排号 |
| `synchronized`/CAS | 不可变更新(阶段 2 见) | 前端用"不动"代替"锁住" |
| Bean Validation | zod(阶段 3 见) | 边界上的体检 |
| 没 `get()` 的 Future,异常烂尾 | unhandledRejection,崩进程 | 前端更记仇 |

## 4. 类比失效清单(答辩必考,误解本常客)

1. **"await 会阻塞"** —— 它阻塞的是这个 async 函数的控制流,不是任何线程。用"让出"造句,不许用"等待"。
2. **"Promise.all 是并行计算"** —— 是并发**等待**。单线程没有并行计算,只有并行 I/O。
3. **"TS 类型运行时还在"** —— 蒸发了。接口数据照样可能是垃圾,校验另请 zod。
4. **"readonly/const = 不可变"** —— 只是引用不动,对象能被掏。真不可变阶段 2 再谈。
5. **"`setTimeout(fn, 0)` 立即执行"** —— 排进下一轮宏任务;前面有微任务清不完,它就永远轮不到。
