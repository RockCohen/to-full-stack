# S41 实验卡 · 全链路联调:三个端,一份真相

> 代码落点:`capstone/`(M1~M4 里程碑进行中)。本卡是联调期的"排障手册+预测题"。
> 每个实验都对应一个你学过的机制——联调翻车几乎全是"旧知识忘了在两端都生效"。

## E1 · 两端一致性:失效链路的最后一块

Web 端支付成功后列表立即刷新(你写的 invalidate),RN 端还显示"待支付"。

- 预测:问题出在服务端、Web 端还是 RN 端?按"读永远是权威副本"的原则排查,列出你的检查顺序。
- ❓排查顺序:① RN 端有没有 `invalidateQueries`(最常见:忘了复制这条纪律);② 两端 queryKey 是否同构(服务端状态只有一份,**缓存坐标必须同构**);③ RN 连的 API 和 Web 连的是同一个吗(App 里的 `localhost` 是手机自己!用电脑局域网 IP)。

## E2 · 跨源的两副面孔

Web 端被 CORS 拦,App 端却直连成功。

- 预测:为什么 RN App 没有 CORS 问题?这说明 CORS 防的到底是什么?
- ❓CORS 防**浏览器里的用户**(Cookie 可被自动携带的跨站读写);App 是"无源客户端"(≈ 你的 curl,没有执法者)。推论:**CORS 不是你的安全边界**——App 直连的世界里,鉴权(JWT)、限流、幂等才防得住人。S27 的"立法在服务端"在 Capstone 里的完整版:**响应头管浏览器,鉴权管所有人**。

## E3 · 幂等:你的老本行,前端的最后一课

用户双击支付按钮,`POST /pay` 发了两次。

- 预测:服务端 mock(409 兜底)之外,前端该在哪一层止血?至少说出两层。
- ❓① 交互层:请求进行中禁用按钮(`isPending` from useMutation);② 语义层:幂等键(Idempotency-Key header ≈ 你支付系统的唯一流水号);③ 服务端兜底:409/唯一约束。**"网络会重试、用户会手抖"是分布式系统的默认设定**——这一课前端和后端是同一课。

## E4 · 发布顺序:三端不是同时上线的

API 改了字段名(`paid` → `payStatus`),老版本 App 还在线上跑。

- 预测:直接上线会发生什么?向后兼容的发布顺序是什么?
- ❓老规矩:**先加后删**(新旧字段并存 → 三端迁移完成 → 删旧字段),≈ 你数据库改列名时的 expand-migrate-contract。OTA 让 RN 的 JS 层可以热更,但**原生层的变更仍要发版**——发布节奏由"最慢的那一端"决定。
