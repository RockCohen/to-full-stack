## E1 · 过桥安检:哪些值能跨语言边界

`bridgeSerialize(v)` 模拟旧 Bridge 的 JSON 序列化安检:

- 预测:数字/字符串/普通对象/数组里的 `undefined`/**函数**/`Symbol`/循环引用,各会怎样?
- ❓对照:JNI 里你传的不是 `String` 是 `jstring`——**跨语言边界的值永远受"边界类型系统"约束**。旧 Bridge 把这约束推给 JSON(函数静默变 `{}`);JSI 的解法不是更好的序列化,而是**不序列化**(E2)。

## E2 · 旧 Bridge vs JSI:一次调用的两种命运

同一个"原生方法调用"(获取订单数),两种通道:

- 预测:① 旧 Bridge(JSON 过桥)是同步还是异步?传 1 万条订单要付什么代价?
  ② JSI(直接引用)同步调用,还需要序列化吗?
- ❓JSI ≈ JNI 的 native 方法表:JS 持有原生对象的引用,直接调。**新架构的价值不是"更快"这么粗糙,是复杂度归位**:能同步的同步、该异步的异步,且不用为每次跨界付序列化税。

## E3 · 线程模型:谁阻塞谁

- 预测:JS 线程跑一个 200ms 的死循环(模拟重计算),原生 UI(动画/滚动)会卡吗?
- ❓RN 的三条线:JS 线程(你的逻辑)、原生 UI 主线程(渲染/手势)、后台线程(模块)。**JS 卡死 ≠ UI 冻结**(动画由原生驱动),但 JS 卡死会让"UI 等 JS 响应"的交互(按钮回调)失灵——≈ 你往单线程的 Netty EventLoop 里塞了阻塞任务,管道没死但响应停摆。所以重计算要么拆片(阶段 0 的让出),要么下沉原生模块。
