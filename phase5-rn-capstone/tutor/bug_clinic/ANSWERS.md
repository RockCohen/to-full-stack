## 门诊 1 · bug1_flatlist_key.tsx

**症状复盘**:标记 A-001 已支付 → 删掉第一行 → 幸存行显示错乱、"双击确认"状态跑到别人的行上。

**根因**:`key={index}` 让实例身份绑在**位置**上。删除首行后,位置 0 的实例(前 A-001,行内 `confirming` 状态还在)收到 A-002 的 props——**主键漂移 = 行内状态串位**。与 phase2 门诊 1 号同源,FlatList 的 `keyExtractor` 是同一契约。

**最小修复**:`key={o.id}`(FlatList 用 `keyExtractor={(o) => o.id}`)。

**后端对照**:用行号当主键,删一行全表外键错乱。**身份必须来自业务,不来自位置。**

**变体思考**:列表"只增不删、纯展示"时 index 安全吗?边界条件是什么?

## 门诊 2 · bug2_navigation_leak.tsx

**症状复盘**:返回列表屏后,详情屏的轮询每秒照跑;若回调里还有 setState,还会收到"对已卸载组件更新状态"的警告。

**根因**:RN 导航是**栈**——从详情页 A push 到别处,A 只是被"盖住",**没有卸载**;interval 没人清,引用链不断,GC 够不着(≈ 忘 close 的连接)。卸载只发生在**出栈**时。这是 phase1 门诊 2 号(监听器泄漏)的 RN 常态化:Web 上"离开即销毁"兜了底,RN 的栈把兜底撤了。

**最小修复**:effect 返回清理函数——`return () => clearInterval(timer);`。进阶:轮询还要感知屏幕焦点(`useFocusEffect`:失焦暂停、回焦恢复),因为"盖住的屏"既没卸载也不该活跃。

**后端对照**:连接池的连接必须 close;写进 `@PreDestroy` 的资源,别指望调用方"记得"。

**变体思考**:哪些资源在 RN 里必须走清理函数?至少列四个(interval、订阅、监听器、进行中的请求/AbortController)。

## 门诊 3 · bug3_bridge_serialization.ts

**症状复盘**:`endpoint`/`retries` 完好,`onProgress`(函数)与 `tag`(Symbol)静默变 `undefined`——没有报错,没有日志。

**根因**:`JSON.stringify` 的规则:函数与 `undefined` **直接跳过**(对象里不报错也不保留),Symbol 同样跳过。旧 Bridge 把 JS 值压成 JSON 文本过桥,一切"不可 JSON 化"的值都**静默蒸发**。静默丢失比崩溃危险:原生侧拿着 `undefined` 回调,要么空指针要么"从不通知进度",查起来没有第一现场。

**最小修复**:旧 Bridge 架构下,回调过桥要**注册-引用**模型(把函数登记在 JS 侧的表里,桥上传表 ID,原生侧发事件、JS 侧查表回调)。JSI 则根本不需要:直接持有原生对象引用,同步调用,零序列化。

**后端对照**:JNI 的 `jstring` 不是 `String`——跨界类型必须按边界契约转换;发消息丢函数 ≈ MQ 里你本来就不能把"方法"当消息体,能传的是"事件描述"。

**变体思考**:安检是白设计了吗?(不是——JSI 下"值约束"变成"引用约束":函数不过桥了,但**生命周期**成了新麻烦,JS 引用原生对象谁来释放?≈ JNI 的 LocalRef/GlobalRef。)

## 门诊 4 · bug4_permission_denied.md

**症状复盘**:拒绝授权 → 启动即崩;"永不允许"的用户连首页都进不去。测试测不出来,因为测试没拒绝过。

**根因**:代码假定了"权限已授予"这一种世界。`getCurrentPositionAsync` 在拒绝态抛异常,无人接住 → 崩溃。**权限拒绝不是异常路径,是正常业务分支**——而且"本次拒绝"与"永久拒绝"(系统设置关闭)必须分流:前者下次可再问,后者只能引导去设置页。

**最小修复**:三态处理——`requestForegroundPermissionsAsync` 先行:授予 → 正常功能;本次拒绝 → 降级 UI("开启定位后可打卡",功能入口置灰但 App 可用);永久拒绝 → 引导弹窗带"去设置"跳转。启动流程不得因任何权限状态阻塞。

**后端对照**:调第三方接口"对方未授权"是你早就处理烂熟的分枝;这里"对方"是用户,而且**审核员会故意拒绝你**。

**变体思考**:为什么 iOS 审核对"拒绝权限后崩溃"零容忍?(审核员站在"最挑剔的用户"视角——你的异常路径就是他的主路径。)

## 门诊 5 · bug5_ota_stale_bundle.md

**症状复盘**:OTA 立即全量推送了修复,一天后仍有用户跑旧界面。

**根因**:OTA 的生效模型是**下载 → 安装 → 激活**,激活默认在**下一次冷启动**——没重启的用户永远在新包门外;还有下载失败回滚、以及"商店原生版 + 从未连网"的用户根本不在 OTA 覆盖内。"立即全量"把这三类人全忘了。

**最小修复**:发布策略——灰度(1%→10%→100%,按用户分桶)、监控新包激活率与崩溃率、保留一键回滚(把"当前指向"拨回旧 bundle);客服侧要求 App 上报版本号(bundle version + native version),先确认"用户到底在哪个版本"再答复。**原生变更(依赖/权限/图标)OTA 无能为力,必须走商店发版。**

**后端对照**:配置中心热下发同款三问:多久拉一次、拉到何时生效、拉不到怎么办。答案也同款:灰度、可回滚、版本可观测——**热更的价值 = 生效快;热更的风险 = 跳过了商店审核,所以可观测与回滚必须自己补上。**

**变体思考**:为什么说"发布节奏由最慢的一端决定"?三端(Web 即时 / OTA 按启动 / 商店按审核)上,一次"改字段名"级联发布的正确顺序是什么?(提示:先加后删 + 三端迁移窗口。)
